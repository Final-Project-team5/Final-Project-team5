## 1. 서비스 컨셉 (확정)

- **핵심 차별점**: 예쁜 문구가 아니라 **법적으로 문제없는 광고 문구**를 생성
- **규제 필터링**: 표시광고법·식품표시광고법·화장품법 등 금지/주의 표현 자동 검사. 생성 → 검증 → block/warn 플래그 → 통과한 것만(또는 경고와 함께) 출력. 룰 사전은 계속 확충 예정 (도혁님)
- **대표 데모 사례**: 건강기능식품/화장품 과장 광고 (예: "아토피 치료되는 크림" → block)
- **타깃 도메인**: 우선 **푸드 / 뷰티 / 굿즈** 3개 업종 (PM 확정, 8/4). 패션은 우선순위에서 제외.
- **K-컬처 정체성**: 이번 1차 서비스에서는 반영하지 않음 — 추후 고도화 단계에서 다룰 요소로 보류 (PM 확정)
- **성능 우선순위**: 모델 퀄리티 >>> 응답 시간 (무거운 모델·다단계 파이프라인 허용)
- **입력 방식**: **챗봇(도우미)이 메인 인터페이스** — 순차 질문형 흐름으로 정보를 채움 (8/5 최종 확정, 아래 참고)
- **AI 생성물 표시 의무 (인공지능기본법 제31조)**: 생성형 AI 결과물에는 AI로 생성됐다는 사실을 표시해야 함. 이미지 내 표기(지우님 후처리)와 화면 고지(소원님 프론트) 두 군데로 나눠 대응 — 상세는 4장 참고
- **서비스명/브랜드 변경 (8/11 팀 확정, 작업 진행 중)**: "AD메이커" → **"애드지니"**로 변경. 컬러 테마도 초록 → **보라(#7B5FEA)/파랑(#4D7FFF)/핑크(#FF6FA8)** 톤으로 변경(핑크는 로고 등 포인트로만 사용, 규제 배지 색상은 브랜드 컬러와 분리해 신호등 색 유지). "그림 그려주는 지니" 컨셉의 마스코트 캐릭터(idle/working/success/face 4종)를 홈·사이드바 로고·챗봇·로딩·완성 화면에 배치 완료 (8/12)
- **고도화 방향 — 무형 서비스업 확장 (8/13 팀 확정)**: 지금까지는 "사용자가 제품 사진을 갖고 있다"는 전제(image2img)로 푸드/뷰티/굿즈 3업종만 지원했으나, **text2img를 도입해 제품 사진 없이도 포스터 제작이 가능**하도록 확장. 이에 따라 무형 서비스업/공간 기반 업종까지 지원 범위를 넓히기로 하고, 프로젝트 기간을 고려해 **2개 업종만 추가**하기로 결정. 최종 확정 업종: **학원 / 체육관·도장**(규제 필터 차별점 + 이미지 생성 안정성 절충안, 성형외과는 의료광고 사전심의 대상이라 제외, 세무·법무는 이미지 쪽에서 밀림, 청소·스터디카페는 규제가 약함). 상세 흐름은 3-3장 참고

## 3. 전체 사용자 플로우 (메인형 챗봇 확정, 8/5)

> 카드/칩 직접 클릭형(서브 챗봇 병행)과 챗봇 메인형 두 버전을 목업으로 비교한 결과,
> **메인형이 선택 과정이 간결하고 카테고리 밖 선택지 등록도 편리하다는 PM 피드백에 따라 메인형으로 확정.**

```
[홈 화면]
좌측 사이드바: 로고, [새로 만들기] 버튼, "오늘의 광고 규제 한 줄"(순환 티커), AI 생성물 사전 고지 문구

     ├─ 통과 → 문구 확정

     [로딩 A] "초안 생성 중" (하위 체크: 키워드 분석 중 / 문구 초안 생성 중)
```

**✅ 사이즈 선택 시점 확정 (8/8, PM 논의)**: 용도별 사이즈(SNS/배너/상세페이지)는 **최종 화면 토글이 아니라, 챗봇 용도 질문 단계에서 선택 → 시안 생성(`/generate/drafts`) 전에 비율로 매핑해서 전달**. 3:1(배너)·3:4(상세) 시안은 생성 전에 비율을 알아야 만들 수 있기 때문. 매핑: SNS 카드뉴스=1:1 / 배너=3:1 / 상세페이지=3:4. → **화면 E의 사이즈 토글은 제거**. 참고: 비정사각 AI 배경은 **3:1(배너)은 지원**, **3:4(상세페이지)만 production 차단**(투명 제품 continuation 문제, 8/10 지우님) — flat 배경(단색/그라데이션)은 3:1·3:4 모두 비정사각 완료됨
- **[1차 미포함] "같은 배경으로 다른 비율 만들기"** (8/10 팀 논의로 정리): 최종 화면에서 배경 유지한 채 다른 비율을 만드는 기능은, 비율이 시안 생성 전에 확정되는 현재 흐름상 지원 안 됨. flat 배경은 같은 설정으로 새 캔버스 재합성이 가능하고, AI 배경은 크롭/outpainting이 필요해 **flat/AI 각각 별도 구현**이 필요함. 1차 서비스에서는 넣지 않고, 필요 시 이후 각 방식에 맞게 추가 (7장 참고)

**중요**: 로딩이 총 2번(초안 생성 → 고품질화) 발생 — UI에서 이 두 단계를 명확히 구분해서 보여줘야 사용자가 "왜 또 기다리지" 하고 이탈하지 않음.

**⚠ 주의 — 실제 개발 시 놓치지 말 것**
- **제품 사진 업로드 기능**: 목업(HTML)에는 빠져있으나 실제 구현 필수. 있으면 inpaint, 없으면 text2img 모드로 자동 분기. 챗봇 흐름 중 자연스러운 시점(예: 2번 질문 근처)에 삽입 위치 결정 필요
- 문구 위치 조정 화면에서 위치에 따라 텍스트 레이아웃(세로/가로 등)이 바뀌는 동작은 **목업(HTML) 한정 임시 동작**이며 실제 구현 대상 아님 — 문구 형태는 도혁님 쪽에서 고정되어 내려옴

### 3-1. 챗봇 API 구조 (도혁님, 8/5 확정)

```
POST /suggest/options (또는 동일 계열 엔드포인트)
{ step, spec }  ← spec은 프론트가 들고 다니는 stateless 값 (포스터 API와 동일 패턴)
```
```
{
  step, total_steps,          // 진행률 표시용 (n/total_steps 단계, 서버가 total_steps 내려줌)
  question,                    // 이번 질문
  options: [...],              // 선택지 4개 (기타는 프론트에서 추가)
  spec: { keywords: [...] },   // 지금까지 채워진 값 → 메인 키워드 칩에 바로 매핑 가능
  confirm_message,             // 선택 종류에 맞는 확인 문구 (서버가 생성)
  done: true | false           // 마지막 단계 완료 시 true
}
```
- `target_slots` 옵션 추가 예정 — 특정 항목만 지정해서 물어보는 것도 가능해지지만, **현재는 메인형(1단계부터 순서대로)으로 확정**했으므로 이 옵션은 사용하지 않음. 추후 서브 보조 기능이 필요해지면 재검토
- `step`/`spec`을 요청에 같이 보내면 중간 단계부터 시작 가능한 구조 (뒤로 가서 답변을 바꾸는 흐름은 이번 스코프 제외 — 7장 보류 항목 참고)
- `COPY_MOCK` 모드 있음 — API 키/실 모델 없이도 프론트 연동 테스트 가능

### 3-2. 로딩 A/B — 실제 진행 상태 반영 여부 (8/12 결정)

**배경**: PR 리뷰에서 "로딩 화면 체크리스트가 실제 모델 진행 상태를 반영하는지, 아니면 시간에 맞춰 자동으로 넘어가는 연출인지" 질문이 나옴. 확인 결과 현재는 **연출**(정해진 시간에 맞춰 자동 진행)이며, 실제 진행 상태 반영은 아님.

**지우님(포스터 모델) 확인 내용** (8/12):
- `/generate/drafts`, `/generate/refine`는 요청 처리가 모두 끝난 뒤 한 번에 응답하는 **동기 구조** — 현재는 프론트가 실시간으로 처리 단계를 받을 방법 없음
- 모델 내부적으로는 전처리 → 이미지 생성 → 후처리/합성 단계가 나뉘어 있어서, 각 단계 진입 시점을 상태로 노출하는 것 자체는 가능함
- 다만 실제 프론트까지 전달하려면 **`job_id` 기반 polling/status API 또는 SSE 같은 별도 구조**가 필요 — 응답 필드 하나 추가하는 수준이 아님
- 현재 응답에는 완료 후 **`elapsed`(총 소요 시간)** 필드가 내려오고 있음(5장 API 스펙 참고)

**결정 사항**:
- 1차 연동에서는 **지금처럼 예상 시간 기반 체크리스트 연출을 유지**
- 실연동 후 실제 `/generate/drafts`, `/generate/refine`의 평균 `elapsed` 값을 확인해서, **체크리스트 각 단계 타이밍(현재 mock의 임의 초 단위)을 실제 평균 처리 시간에 비례하도록 재조정**
- 실시간 진행 상태(polling/SSE 기반)는 1차 연동 스코프에서 제외 — **추후 별도 기능으로 필요해지면 그때 지우님과 서빙(태진님) 쪽과 함께 설계 방식(polling vs SSE) 재논의**
- 문구 생성(화면 B, `/generate/copy`·`/validate/copy`)은 처리 시간이 짧아 체크리스트 없이 진행 — 로딩 A/B는 이미지 생성(화면 C/D)에만 해당

### 3-3. 챗봇 흐름 확장 — 무형 서비스업 (방식 B, 8/13 확정)

**배경**: 위 1장 고도화 방향에 따라 챗봇 0단계가 새로 필요해짐. 방식 두 가지를 놓고 팀 투표:
- 방식 A: 1단계 업종 선택지에 무형 서비스업을 그냥 추가 (사진 업로드 서브스텝은 그대로 두고 "없음" 클릭)
- **방식 B(채택)**: 0단계로 "제품이 있으신가요, 서비스 위주이신가요?"를 먼저 물어 흐름을 분기 — 제품형이면 기존 흐름(사진 업로드 서브스텝 포함) 그대로, 서비스형이면 무형 서비스업 선택지로 가고 **사진 업로드 서브스텝은 아예 스킵**

**핵심 결정** (도혁님 chatbot.py 반영 기준):
- 0단계에서 `business_type`("product" | "service")을 먼저 확정
- 제품형: 기존 흐름 유지 (푸드/뷰티/굿즈 + 사진 업로드)
- 서비스형: 확정 업종(학원/체육관·도장) 선택지로 가고 사진 업로드 단계는 프론트가 렌더하지 않음 (서버는 사진 존재 자체를 모름 — 사진 업로드는 챗봇 슬롯이 아니라 프론트 서브스텝이라 프론트가 판단)
- 4~6단계(느낌/강조점/추가요청) 중 **강조점(5단계) 선택지가 업종군에 따라 다른 세트**로 제공됨 — 제품형: 신선함/품질, 합리적 가격, 이벤트·혜택, 제품 특징 / 서비스형: 전문성·경력, 후기·평판, 접근성(위치·시간), 상담·가격 안내. 톤(4단계)과 용도(2단계)는 공통
- 3단계 질문 문구만 서비스형은 "어떤 서비스나 가게를 홍보하시나요?"로 달라짐
- **분기 로직은 전부 서버(chatbot.py)가 지고, 프론트는 `business_type` 값만 spec에 실어서 넘기면 됨** — 업종 선택지·강조점 세트 교체는 서버가 알아서 처리
- **하위호환**: `business_type` 없으면 "product"로 간주 — 기존 연동 코드가 깨지지 않음

**spec 필드 추가**:
```
business_type: "product" | "service"   // 0단계에서 확정, 이후 요청에 계속 실어서 전달
```

**서비스형 업종(1단계 선택지)**: 학원, 체육관·도장 (8/13 최종 확정)
- 규제 근거: 표시광고법("지역 1위", "국내 최고" 등), 국민체육진흥법(체육지도자 자격 표현), 방문판매법("환불 불가", "중도 해지 불가"), 학원 관련 과대광고("합격 보장", "1등", "단기간 완성") — 도혁님 쪽에서 규제 룰 확장 및 검증 케이스 편입 예정
- 이미지 생성 관점(지우님 확인): 공간·운동기구 중심 구도는 비교적 안정적, **다만 여러 사람이 대련하거나 복잡한 자세를 취하는 장면은 이미지가 깨질 가능성이 있어 데모에서는 지양**

**0단계 질문/선택지 문구 (프론트 하드코딩, 8/14 확정)**:
```
질문: "제품이 있으신가요, 서비스 위주이신가요?"
선택지:
- "제품이 있어요 (사진 촬영 가능)"
- "서비스 위주예요 (사진 없이 진행)"
```
0단계에서는 지원 업종(학원/체육관 등)을 미리 언급하지 않는다 — 실제 업종 목록은 1단계에서
자연스럽게 노출되므로, 대신 **1단계 화면에 "업종은 계속 추가할 예정이에요" 같은 짧은 안내
문구를 넣어서**, 서비스형 업종이 두 개뿐인 걸 보고 사용자가 실망하지 않도록 처리한다(8/14).

**0단계 / 사진 업로드 처리 방식 — 확정 (8/13, 도혁님 확인)**
- **0단계(business_type 질문)는 서버가 안 내려줌 — 프론트가 하드코딩**: 0단계 시점엔 아직 business_type을 모르는 상태라 서버가 내려줄 선택지 자체가 없음. 프론트가 첫 화면에 고정 질문("제품이 있으신가요, 서비스 위주이신가요?")을 하드코딩해서 물어보고, 그 값만 spec에 담아 1단계부터 `/suggest/options` 호출 시작
- **사진 업로드 스킵도 프론트 판단**: 사진 업로드는 챗봇 슬롯이 아니라 프론트 서브스텝이라 서버는 사진 존재 자체를 모름. `business_type=service`면 프론트가 그 서브스텝을 아예 렌더하지 않으면 됨
- **서비스형 비율/배경 제약도 동일 결론** (도혁님 재확인) — 서비스형은 1:1 고정 + AI 배경만, flat과 비정사각(3:1/3:4)은 프론트에서 같이 잠글 것

**프론트 작업 범위** (API 연동·PR 완료 — 단, 아래 8/14 변경사항 반영 후 착수. 도혁님 chatbot.py 구현 대기 중):
- 0단계 UI 추가 (product/service 선택, 프론트 하드코딩)
- `business_type=service`일 때 사진 업로드 서브스텝 미노출 처리
- spec에 `business_type` 담아 이후 모든 `/suggest/options` 요청에 포함
- **비율×배경 조합 제약 반영** (5장 포스터 모델 섹션 표 참고, business_type 작업과 한 번에 처리): 챗봇 용도 질문에서 불가 조합(사진없음+3:1/3:4, 서비스형+3:1/3:4) 선택 차단, 화면 C에서 서비스형이면 flat 칩 숨김

### 3-4. 챗봇 흐름 대폭 개편 — product는 img2img 고정 + 제품명 질문 제거 (8/14 팀 회의 확정)

**배경**: 8/13까지는 "product는 사진 있을 수도/없을 수도(선택)"였는데, 8/14 회의에서 **product는
무조건 사진 첨부(img2img 고정)**로 방향이 바뀌었다. 동시에 3단계(제품명 텍스트 질문)를 없애고,
사용자가 첨부한 사진을 Vision LLM(gpt-5.4-mini, 이미지 입력 지원 확인됨)이 인식해서
`spec.product`를 자동으로 채우는 방식으로 전환한다. 이유: 3단계 선택지를 LLM이 즉석 생성하면서
뷰티 카테고리에 "네일샵"/"헤어샵"처럼 형체 없는 무형 서비스가 계속 섞여 나오는 문제(3-3장 논의)가
있었는데, 애초에 제품형은 사진으로만 판단하게 하면 이 문제 자체가 발생할 자리가 없어짐.

**변경된 흐름**:
```
0단계(business_type, 프론트 하드코딩)
  → product: "제품 사진을 첨부해주세요" (필수 업로드, "없음" 선택지 없음 — 사진 없이 진행하는
     경로 자체를 차단)
  → service: 기존대로 서비스 정보 입력(사진 없음 고정)
1단계(업종)
2단계(용도) — 완전 하드코딩(아래 표 참고)
3단계(구 제품명 질문 → 사진 업로드로 교체)
  → 사진 첨부 즉시 Vision LLM이 인식 → spec.product 자동 생성 (사용자 직접 입력 없음, "기타"도 없음)
  → 인식은 4·5단계보다 먼저 이뤄져야 함 (5단계 강조점 선택지가 인식된 제품에 맞게 나와야 하므로)
  → 예상 소요 2~5초, 프론트에서 짧은 로딩 UI 필요(화면 C/D의 큰 체크리스트까지는 불필요, 인라인
    스피너 정도)
4단계(느낌/tone)
5단계(강조점/keywords) — 인식된 제품 기반으로 서버가 생성
6단계(추가요청/request)
```

**2단계(용도) 하드코딩 확정** — LLM 즉석 생성 대신 완전 고정, "기타" 선택지도 없앰(용도는
결국 비율 3가지 중 하나로 귀결되는 값이라 자유 입력 실익 없음):

| business_type | 노출 선택지 |
|---|---|
| product | SNS(1:1) / 배너(3:1) / 상세페이지(3:4) — 세 개 다 고정 노출 |
| service | SNS(1:1)만 고정 노출 — 배너·상세는 선택지 자체에서 제외 (미지원 안내는 프론트가 별도 처리) |

**제품 사진 업로드 안내 문구 (신규, 프론트 반영)**: 사진 인식 정확도와 포스터 생성 품질을 위해
업로드 단계에 아래 안내를 노출한다.
> "최대한 깨끗한 배경(단색)에 제품이 1개만 나오도록 찍어주세요."

**진행 상황 단계 수 — product 7단계 vs service 6단계 (8/14 발견)**: 0단계(business_type
선택)가 프론트 하드코딩이라 서버는 이 단계를 모른다. product는 0단계+1~6단계로 **총 7단계**,
service는 3단계(사진 업로드)가 렌더 자체가 안 되므로 0단계+1~6단계라도 실질 노출 단계는
**총 6단계**다. 사이드바 진행 상황 위젯(`n/total_steps`)이 business_type에 따라 분모가
달라져야 함 — 서버가 내려주는 `total_steps`(1~6단계 기준일 것으로 예상)에 프론트가 0단계를
포함해 +1 하는 보정 로직이 필요하다. 화면 A 진행률 표시도 동일하게 반영.

**규제 검증 시점 (8/14, 지우님 흐름도 관련 확인 필요)**: 지우님이 정리한 흐름도에는 "제품
인식 → 규제 룰 검증 → 정보 구조화" 순서로 그려져 있었으나, 규제 검증은 원래 **문구가 만들어진
뒤**(생성/재검증 시점)에 이뤄지는 것으로 알고 있어 순서가 다를 수 있음 — 도혁님 확인 요청함.

**비용 검토 (8/14)**:
- **Vision 인식(이미지 입력, gpt-5.4-mini)**: 이미지 1장 인식에 약 $0.0017(약 2~3원) 수준으로
  추정. 문구 생성/규제 검증과 비슷한 저비용 — 우려할 수준 아님
- (검토 후 기각) **GPT-Image로 특정 카테고리(예: 음식) 직접 생성 + 배경만 로컬 합성**하는
  방안도 논의됐으나, 이미지 생성은 토큰이 아니라 장당 과금(GPT Image 1 mini 최저 $0.005~,
  일반 품질 약 $0.034/장)이라 로컬 diffusion(추가 과금 없음) 대비 비용이 크게 늘어 기각.
  로컬 SD15/SDXL의 음식 이미지 품질 문제는 다른 방식으로 개선 검토

**미해결 논의 — 무형 서비스업(service) 자체의 필요성**: 오늘 product 흐름까지 여러 차례
수정(사진 유무 선택 → img2img 고정)하게 만든 근본 원인이 service 분기를 매끄럽게 처리하려는
과정에서 나온 것이라, service 지원 자체의 실익 대비 구현 복잡도가 계속 논의 대상으로 남아있음.
현재는 PR #62(business_type 분기)까지 구현된 상태라 유지하는 방향으로 진행 중이나, 필요시
재검토 가능.

**프론트 작업 범위 (수정, 도혁님 chatbot.py 재구현 대기 중이라 아직 착수 전)**:
- 0단계 UI (product/service 선택, 프론트 하드코딩) — 기존과 동일
- 1단계 화면에 "업종은 계속 추가될 예정" 안내 문구 추가 (서비스형 업종 2개뿐인 것에 대한 기대치 관리)

### 3-5. 배경 레퍼런스 특징 추출 + AI Design Planner 연결 방향 (8/18 최신 결정)

**배경**: 8/14 회의에서 product 흐름의 이미지 입력을 **제품 사진 1장 필수 + 배경 레퍼런스 이미지 1장 선택**으로 확정했고, 사용자가 고른 `tone`/`keywords`/`request` 같은 추상적인 값을 이미지 생성 모델이 이해하기 쉬운 시각 표현으로 구체화하는 **AI Design Planner**를 내부 처리 단계로 두기로 했다. 8/18 팀 논의에서 배경 레퍼런스도 단순 보관하지 않고, 별도 Vision으로 특징을 추출해 Design Planner 입력으로 활용하는 방향이 추가로 정리되었다.

**최신 결정 / 방향 (8/18)**:
- 제품 이미지와 배경 레퍼런스 이미지는 **역할을 완전히 분리해 관리**한다.
  - `productImage`: 필수. 제품 Vision 인식 및 포스터 생성의 원본 제품 이미지에 사용.
  - `backgroundReference`: 선택. 제품 Vision에는 전달하지 않고, 배경 특징 추출에만 사용.
- 배경 레퍼런스가 있을 때만 별도 Vision endpoint **`POST /vision/background`**로 특징을 추출하는 방향으로 진행한다.
  - 추출 대상: **색감 / 조명 / 질감 / 분위기 / 구도**
  - 제품 이미지처럼 사용자에게 `[맞아요] / [수정할게요]`로 재확인받는 단계는 **두지 않는다**.
- 배경 특징은 `spec.product`에 합치지 않는다.
  - `spec.product`는 PR #70 기준 **사용자가 확인·확정한 제품명 전용 슬롯**으로 유지한다.
  - 배경 특징은 별도 **`spec.background_context`**로 분리해 관리하는 방향이다.
  - 이유: 제품 정보와 배경 정보가 섞이면 문구 생성·규제 검증 근거가 오염될 수 있음.
- `spec.background_context`는 이후 **AI Design Planner의 Visual Prompt 입력값**으로 활용한다.
  - 예시 입력: `product + tone + keywords + request + background_context`
  - Design Planner는 사용자에게 질문을 하나 더 추가하는 단계가 아니라 **내부 LLM 처리 단계**이므로, 사용자 진행률은 기존과 동일하게 **product 7단계 / service 6단계**를 유지한다.
- Design Planner의 최종 출력물을 poster 모델에 어떤 필드명/요청 구조로 전달할지는 **지우님 poster API 계약 확정 후 연결**한다. 프론트에서 임의로 필드명을 확정하지 않는다.

**현재 구현 상태 (프론트, 8/18)**:
- `productImage` / `backgroundReference` state 및 업로드 UI는 **분리 구현 완료**.
- 제품 사진 1장 필수 + 배경 참고 이미지 1장 선택을 **같은 사진 질문 카드 안에서 별도 섹션**으로 제공한다.
- 배경 이미지는 현재 **Vision / copy / poster API body에 아직 포함하지 않음**.
- `planDesignPrompt(spec)` 연동 지점만 미리 준비되어 있고, 현재는 기존 `buildPrompt(spec)`를 그대로 반환하는 **pass-through** 상태다.
- 실제 `/vision/background` 연동 및 `background_context` 전달은 **백엔드 endpoint 확정/구현 후 후속 작업**으로 진행한다.

**상태 구분**:
- 제품/배경 이미지 역할 분리: **확정 / 프론트 구현 완료**
- 배경 특징 추출 필요성 및 `background_context` 분리 방향: **8/18 팀 논의 기준 채택 방향**
- `POST /vision/background`: **도혁님 제안 / 백엔드 구현 전**
- Design Planner 실제 endpoint·스키마: **미확정 / 미구현**
- poster 모델 전달 필드: **지우님 API 계약 대기**

### 화면 A — 챗봇 진행 화면 (구 카테고리·키워드·문구 입력 단계 통합)
- 챗봇이 5개 질문을 순서대로 진행, 답변은 대화 말풍선으로 누적 표시

- 4번(강조점, 복수 선택) 답변 즉시 5번 질문으로 자동 연결 (중간 확인 버튼 없음)
- 5번(추가 요청, 자유 입력) 답변 후 [이 내용으로 완료] 버튼으로 마무리
- 상단에 진행률 표시 (n/total_steps 단계, 서버 응답 기반)
- **제품 사진 업로드는 이 흐름 중 반영 필요** (구현 시 놓치지 말 것)
- **용도 질문 → 비율 매핑** (8/8~10 확정, 8/10 서버 반영): 챗봇에 용도 질문 추가(업종 다음 단계). **매핑은 서버(도혁님)가 처리** — `/suggest/options` 응답 `spec`에 `purpose`(sns/banner/detail)와 `aspect_ratio`(1:1/3:1/3:4)가 함께 채워져 옴. **프론트는 매핑 계산 없이 최종 `spec.aspect_ratio`를 `/generate/drafts` 요청에 그대로 전달**만 하면 됨. 매핑: SNS=1:1 / 배너=3:1 / 상세페이지=3:4. (refine 단계에선 draft 크기로 비율 추론되므로 다시 안 보내도 됨). 특정 화면에서 용도만 물으려면 `target_slots=["purpose"]` 사용 가능
- **⚠ 실연동 전 필드명 교체 필요** (8/11, 지우님 PR #44 리뷰): `posterApi.js` mock 내부에서 파라미터명을 `ratio`로 쓰고 있는데, 실제 포스터 서버 필드명은 **`aspect_ratio`**임. mock이라 지금은 문제없지만, 실서버로 교체할 때 `ratio` → `aspect_ratio`로 이름을 맞춰야 함
- **⚠ text2img(사진 미업로드) + 비정사각(3:1/3:4) 조합 미지원** (8/11, 지우님 PR #44 리뷰): 현재 포스터 서버는 제품 사진 없이(text2img) 3:1/3:4 비율 생성을 지원하지 않음(400). 우리 화면 A는 "용도 선택"과 "사진 업로드 여부"를 독립 질문으로 설계해뒀어서, 사용자가 사진 없이 배너/상세페이지를 고르면 실연동 시 막힐 수 있음. 지우님 확인 결과 **후속 구현 예정** — 현재는 화면 그대로 두고 홀드, 실연동(12~13일 예정) 시점에 구현 여부 재확인 후 필요하면 화면 흐름(사진 업로드 순서 또는 3:1/3:4 비활성화) 조정
- **포스터 서버 후속 작업 우선순위** (8/11, 지우님 확정): 현재 PR 안정화 → **GET /fonts → text2img 비정사각(3:1/3:4) → 제품·문구 자동 배치 연동** 순으로 진행 예정. text2img 비정사각은 기존 구조 활용 가능해 구조적으로 어렵지 않음(위 항목 실연동 전 재확인 시 참고). **3:4 AI 배경은 별도 트랙** — 투명 제품 continuation 문제로 의도적 차단 중이라 별도 품질 검증 필요, 위 순서와 무관하게 별도 일정으로 진행
- **⚠ 3:4(상세페이지) 선택 시 AI 배경 제한** (8/10, 지우님): 3:4에서 AI 배경은 투명 제품의 continuation 문제로 현재 production 차단됨. 3:4 선택 시 **단색/그라데이션 배경만 가능, AI 배경은 "준비 중"으로 비활성화** 표시 (화면 C 배경 스타일 선택 UI에서 처리). (3:1 배너 AI는 사용 가능)
- **[논의 중] 챗봇 용도 질문에서 3:4 AI 제한 사전 안내 여부** — 현재는 배경 선택 화면(화면 C)에서만 "준비 중" 표시. 챗봇 용도 질문 단계에서 미리 안내할지(예: "상세페이지 · AI 배경 준비 중")는 팀 논의 후 결정 예정. 챗봇 심플함 vs 기대치 사전 조정 사이 트레이드오프

### 화면 B — 문구 생성 결과 (규제 검증 반영)
- **문구 3개(시안) 중 선택** (8/8 진우님 리뷰 → 8/10 구현 완료): `/generate/copy`가 문구를 **3개(headline/sub 조합)** 반환하므로, 사용자가 3개 카드 중 하나를 선택하는 UI. 각 문구에 규제 배지(block 빨강/warn 노랑/통과) 표시, block 문구(safe: false)는 선택 불가, 선택한 문구만 직접 수정→재검증 동작
- **통과 시**: 생성된 문구 + "규제 검증 통과" 배지
- **block/warn 시**: 걸린 사유 표시 + **대체 표현 제안(`suggestion`) 함께 노출** — block은 빨간 배지, warn은 노란 배지로 구분 (8/6, 도혁님 룰 사전 확충 반영). 대체 문구 제안 + "이 문구로 계속하기" 버튼
- **다음 화면 진행 가능 여부는 `safe` 필드 기준** (8/6 확정) — `safe`는 `severity: "block"`인 flag가 하나라도 있으면 `false`. **warn만 있는 경우는 `safe: true`라 다음 화면으로 진행 가능** (block은 명백한 법 위반이라 막지만, warn은 경계선 표현이라 사용자가 인지하고 넘어갈 수 있음). 배지는 계속 노출되지만 진행 버튼을 막는 건 block뿐
- **직접 수정 옵션**: 사용자가 문구를 직접 편집할 수 있는 입력창 제공 → 수정 완료 시 `/validate/copy`로 재검증 → 재차 block이면 다시 안내
- 이 화면에서 문구가 확정된 후에만 이미지 생성 단계로 진행

### 화면 C — 이미지 초안 선택 (1단계 결과)
- 시안 **3장 고정** 그리드로 표시 (base64 이미지 직접 렌더링)
- **⚠ 실제 drafts 응답 image는 prefix 없는 순수 base64** — 화면 표시 시 `toImageSrc()`로 data URI 변환 필요(`data:image/png;base64,${image}`). refine에 넘길 값은 원본 base64 유지 (8/8, 지우님 리뷰). background echo는 현재 구현에서 정상 확인됨
- 각 시안 클릭 시 선택 표시(테두리 강조 등) + 선택한 시안을 화면 하단(또는 별도 영역)에 크게 확대해서 보여줌
- **로딩 화면(로딩 A)에서 스켈레톤 카드 3장 미리보기는 8/12 제거 확정** — 체크리스트만 노출, 로딩 종료 후 실제 시안 3장이 한 번에 표시됨(레이아웃 시프트 없는지 확인 완료)
- 다시 생성하기(재시도) 옵션도 함께 제공

### 화면 D — 문구 위치·크기 자유 조정
- 선택한 시안(문구 없는 배경 상태) 위에서 사용자가 문구를 자유롭게 드래그하여 위치 지정
- **폰트 크기: 작게/보통/크게 3단계 프리셋 확정** (8/5)
- 드래그하는 동안은 서버 호출 없이 **프론트 CSS로 실시간 미리보기**만 처리 (즉각 반응)
- [완성하기] 버튼을 누를 때 딱 한 번만 최종 좌표(x, y — 0~1 비율)와 폰트 크기를 담아 서버에 전송
- 문구의 줄바꿈/형태 자체는 도혁님 쪽에서 고정되어 옴 — 위치 이동에 따라 형태가 바뀌는 동작은 없음
- `style`은 이번 단계에서는 `plain` 고정 — 별도 UI 없음 (추후 `bar` 옵션 추가 시 여기에 토글 추가)
- **서체 선택 UI** — 드롭다운(select) 방식, **폰트 1개 선택 → headline·sub 공통 적용**(각각 선택 아님, 8/10 지우님과 확정). **확정 폰트 목록 5종** (8/10, 진우님 완성형 검증): Pretendard, 나눔명조 Bold, Gmarket Sans, Galmuri11, 나눔손글씨펜 — 모두 한글 음절 11,172자 전체 지원(글자 깨짐 없음). 완성형 한정 폰트(2,350~2,781자)와 기호 정규화 필요 폰트(Cafe24 써라운드 에어, GraceSerif)는 이번 목록에서 제외, 추후 정규화 처리 후 추가 검토. **연동 구조**: 프론트 `font_id`(단일) → 백엔드 whitelist → 실제 TTF 매핑. refine 요청 `text.font_id`로 전송. 프론트 미리보기도 동일 웹폰트를 로드해 최종 PIL 렌더와 차이 최소화. font_id 명칭은 지우님과 함께 확정 예정
- **font_weight 파라미터는 만들지 않음** (8/11, 지우님 확정): 굵기가 필요해지면 별도 파라미터 대신 `pretendard-bold`, `gmarketsans-bold`처럼 **굵기별 font_id를 추가**하는 방식으로 감. 1차 범위에서는 기존 5종만 유지
- **[완성하기] 클릭 후 별도의 "고품질화 중" 로딩 화면(로딩 B)으로 전환** — 시안 선택 때의 로딩(로딩 A)과 시각적으로 구분되어야 함
- **/generate/refine 요청 실패/타임아웃 시에도 재시도 버튼 제공** (1단계 재시도와 별개로 구현)
- 미리보기 폰트를 서버 렌더링 폰트와 일치시키고, 드래그 범위에 안전 여백을 둬 미리보기와 실제 결과 간 어긋남 최소화 (8/6 PM 논의)

### 화면 E — 최종 결과

**확정된 정책 (8/13 원본, 대부분 유지)**:
- **제품형은 8/14부터 사진 필수(선택 아님)로 변경** — 8/13엔 "사용자 선택 유지"였으나 3-4장 결정으로 대체됨. text2img 자체가 product 흐름에서는 더 이상 쓰이지 않음(service만 text2img)
- **서비스형은 AI 생성만 제공, flat(단색/그라데이션)은 미지원** (진우님 제안 → 지우님 동의) — 사진이 없으면 제품 누끼·배치·그림자 단계가 전부 빠져 "단색 배경+문구"만 남게 되는데, 공간/장면 자체를 보여줘야 하는 서비스형에는 부적합
- **사진 없는 text2img(=service)는 현재 1:1만 가능** (지우님 확인, 8/13 표 정정) — 3:1 AI는 "품질 문제로 막은 게 아니라, 사진 없는 비정사각 text2img 경로를 아직 안 만든 상태"라 400. 지우님 진행 중인 배경 생성 실험에서 SD1.5 비정사각 품질 확인 후 지원 여부 재검토 예정
- **3:4 AI는 품질 문제로 의도적 차단, 당분간 유지** (기존 확인 + 지우님 재확인) — 세로로 긴 캔버스에서 제품 외형을 임의로 이어 그려 실제 없는 부위가 생성되는 문제(특히 투명 제품), 사전에 안전하게 구분할 방법이 없어 production 차단
- **flat이 사진을 필수로 받는 이유** (지우님 설명): 사진→누끼 추출→제품 배치→그림자 생성→배경 합성 순서로 만들어진 파이프라인이라, 사진이 없으면 사용할 제품 마스크 자체가 없음

**구현 시 유의할 점** (8/6, 지우님 확정 반영)
- **서버가 세션을 저장하지 않는 stateless 구조** — 프론트가 1단계 응답에서 선택한 시안의 `image`(base64)를 상태로 들고 있다가 2단계 요청 때 `draft_image`로 그대로 재전송
- **`original_image`(원본 제품 사진)를 refine 요청마다 항상 전송** — AI 모드에서도 필요. 안 보내면 원본 제품 보존 단계가 빠져서 SDXL이 제품을 다시 그리며 로고/제품명/포장지 한글이 뭉개질 수 있음. solid/gradient 배경 모드나 z_order="behind" 연출 사용 시엔 아예 필수(없으면 400). → **챗봇 초반 업로드한 원본 사진(base64)을 화면 D(refine 호출)까지 상태로 계속 보관해야 함**
- **`background` 값도 refine에 echo** — draft 응답의 선택 시안 `background`를 그대로 다시 보내야 같은 배경 재현(서버 무상태). solid/gradient 모드에서 특히 중요
- **제품 배치(placement)는 drafts 단계에서 결정** (8/11, 지우님): 제품 위치·크기(scale_factor/x/y)는 bbox·clipping·그림자·시안 구도에 영향을 주기 때문에, refine이 아니라 **drafts 요청 시점**에 정해야 함(시안과 최종본 구도가 어긋나지 않도록). 다만 "배경 선택 후 문구+제품 위치를 같이 조정"하는 UX도 자연스러울 수 있어, 실연동 시 재배치 흐름을 프론트와 함께 재검토 예정
- **응답 이미지는 순수 base64** — data: prefix 없이 오므로 프론트에서 `` `data:image/png;base64,${res.image}` `` 로 감싸서 사용
- **문구 위치/크기 필드**: `x`, `y`(0~1 비율, 둘 다 보내야 좌표 모드) / `headline_size`, `sub_size`(짧은 변 대비 비율, 각각 전송). 3단계 프리셋(작게/보통/크게)은 이 비율값으로 매핑해서 보냄. 드래그 UI + CSS 미리보기, 서버 요청은 완성 시 1회만
- **x/y 좌표 기준 — center로 통일 확정** (8/10, 지우님): 프론트 미리보기가 텍스트 박스 중심 기준이라, 백엔드도 x/y 둘 다 **중심 기준으로 통일**하기로 함. **refine 요청 `text.align: "center"`를 명시**해야 함 (생략 시 기본 left라 위치 어긋남). 백엔드가 기존 y(텍스트 상단 기준)를 중심 기준으로 수정 예정. → **프론트 좌표 계산은 그대로 두면 됨**(변환 로직 불필요). 단, 문구 크기는 서버 `auto_fit`에서 공간 부족 시 실제 적용 크기가 작아질 수 있어 미리보기와 100% 일치는 어려움(감안 필요)
- **`style`은 반드시 "plain" 명시** — 기본값이 "bar"라 생략하면 반투명 배경 박스가 깔림
- **문구 중계 역할**: 도혁님 문구 모델 결과(`headline`, `sub`)를 프론트가 받아 `text` 필드에 담아 전달. 프론트는 문구 내용/형태에 관여하지 않고 위치·크기만 결정
- **글자 수 제한(headline 20자/sub 30자)은 프론트가 자르지 않음** — 도혁님 생성 단계에서 자동 축약 1회, 초과 시 `over_limit` 플래그
- **`meta.layout`**(제품 bbox 비율) 활용 가능 — 화면 D 드래그 UI에서 "제품 위/아래 영역에 스냅" 같은 보조 기능에 쓸 수 있음 (선택)
- **문구 재편집 구조 — 문구/배경 분리 방식** (8/10, 지우님): `/generate/refine` 응답은 문구+AI 표시가 이미 합성된 최종본이라, 그 위에 문구를 다시 그리면 기존 문구가 남음. 따라서 향후 문구 수정 기능은 **문구 없이 refine 1회(`ai_notice: false`) → 프론트가 문구·표시 없는 결과 보관 → 문구/위치/크기/폰트 변경 시 별도 텍스트 합성 API 호출 → 마지막에 AI 표시 적용** 흐름으로 설계 예정. 이 방식이면 문구 여러 번 수정해도 diffusion 재실행 불필요. (behind 재편집 지원 여부는 이후 integration 때 범위 결정) — 백엔드 API 구조 지우님이 설계 중
- **AI 생성물 워터마크**: 지우님 후처리 단계에서 이미지 하단 모서리에 반투명 표기 (프론트 작업 아님)
- 결과는 base64로 수신 (URL 방식은 추후 이력 저장 필요 시 재검토 — 7장)

**챗봇(메인 흐름) 순차 질문** (8/5 최종 확인, 도혁님)

실제 필수 필드는 `message` 하나뿐. 프론트가 매 요청마다 챙겨야 하는 건 `message`(사용자가 고른/입력한 값) + `step`(직전 응답의 `next_step` 그대로) + `spec`(누적 상태, 계속 들고 다님) 세 개뿐이다.

```
POST /suggest/options

// 1단계 시작
{ "message": "푸드" }

// 2단계 이후
{ "message": "떡볶이", "step": 2, "spec": { "category": "food" } }
```
```
{ step, next_step, total_steps, question, options: [...], spec, confirm_message, done }
```

**필드별 설명**
- `message` (필수) — 사용자가 선택지를 골랐으면 그 텍스트, "기타"로 직접 입력했으면 그 문장 그대로
- `mode` (기본값 `"fixed"`) — 안 보내면 고정 5단계 흐름으로 동작. 메인형 확정된 지금 방향에서는 생략(기본값 사용)
- `step` (기본값 1) — 응답으로 내려온 `next_step`을 그대로 다음 요청의 `step`에 넣어주면 됨
- `spec` — 서버가 상태를 저장하지 않는 stateless 구조(포스터 API와 동일 패턴)라 프론트가 들고 있다가 매 요청에 같이 전송. 응답 `spec`에 병합되어 내려옴
- `spec.business_type` — **(8/13 신설)** `"product" | "service"`, 0단계에서 확정 후 이후 모든 요청에 계속 실어서 전달. 서버가 이 값을 보고 1단계 업종 선택지·5단계 강조점 세트를 자동 교체. 없으면 "product"로 간주(하위호환). 상세는 3-3장 참고
- `history` — `auto` 모드(자유 대화형)에서만 사용. `fixed` 모드에서는 `spec`이 상태를 대신하므로 생략 가능
- `target_slots` — 특정 항목만 물어볼 때 사용(예: `["tone"]`). 메인 흐름에서는 생략. 서브 보조 기능 필요해지면 재검토 (7장 참고)

5단계까지 완료(`done=true`)되면 `/generate/copy` 요청으로 자동 연결됨. `COPY_MOCK` 모드로 키 없이도 프론트 연동 테스트 가능.
