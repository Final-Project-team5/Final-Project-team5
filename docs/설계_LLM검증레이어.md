# 규제 검증 2차 레이어 설계 (룰 → LLM 하이브리드)

> 상태: 프로토타입(골격 + 라우팅 구현 완료). LLM 판정 효과는 API 키 실행으로 측정 예정.
> 기준일: 2026-08-11 · 관련 코드: `copy_model/regulation_llm.py`, `eval/run_escalation.py`

## 1. 왜 필요한가 (골드셋 실측 근거)

정규식 룰은 맥락을 못 본다. HOLDOUT에서 남은 오류 3건이 모두 같은 원인이다.

| 유형 | 예시 | 룰 판정 | 정답 | 원인 |
|---|---|---|---|---|
| 오탐 | "최고의 하루를 담은 다이어리" | warn | safe | '최고'가 제품이 아니라 '하루'를 수식 |
| 오탐 | "완벽한 오후를 위한 캔들" | warn | safe | '완벽'이 '오후'를 수식 |
| 미탐 | "면역 쑥쑥 올려주는 홍삼" | safe | block | 효능을 의미로 우회 |

셋 다 단어가 아니라 맥락 판단이 필요하다. 룰만으로는 구조적으로 못 잡는다.

## 2. 설계 원칙

1. 룰이 1차 필터(비용 0, 즉시). 명백한 block/safe는 룰을 신뢰한다.
2. LLM은 비싸다. 경계 케이스만 골라 2차로 넘긴다(에스컬레이션). 전건을 LLM에
   보내면 비용/지연이 폭발한다.
3. LLM 판정기(judge)는 주입식. 오프라인/테스트는 가짜 judge로 배선을 검증하고,
   운영은 실제 LLM judge를 쓴다. 모듈이 OpenAI를 직접 부르지 않아 테스트가 쉽다.

## 3. 에스컬레이션 정책 (`escalation_decision`)

| 룰 1차 결과 | 추가 신호 | 처리 | 방향 |
|---|---|---|---|
| block | - | 룰 신뢰, LLM 생략 | - |
| warn | 문맥 최상급 어휘(최고/완벽 등) | LLM 2차 | 다운그레이드 검토 |
| warn | 그 외 | 룰 유지 | - |
| safe | 효능 의미회피 어휘(면역/개선 등, food·beauty) | LLM 2차 | 업그레이드 검토 |
| safe | 그 외 | 명백 정상, LLM 생략 | - |

## 4. 라우팅 오프라인 실측 (효과 아님, 라우팅만)

`python -m eval.run_escalation` (골드셋 81건, judge=None)

- 에스컬레이션율: 12/81 = 14.8% (나머지 85.2%는 룰로 즉시 종료 → 비용 통제)
- 룰 오류 3건(오탐 2 + 미탐 1) 커버리지: 3/3 = 100% (교정 기회를 모두 확보)
- 에스컬레이션 정밀도: 3/12 = 25% (안전 지향 — 정상 safe 9건도 재확인차 포함)

해석: 이 라우팅은 재현율 우선(룰 오류를 하나도 안 놓침)이고, 대신 이미 정상인
경계 문구 일부도 LLM에 재확인시킨다. 규제는 미탐 비용이 커서 이 방향이 맞다.
전체 트래픽의 약 15%만 LLM을 타므로 비용은 통제된다.

## 5. 배선 검증 (가짜 judge)

judge를 주입하면 에스컬레이션된 케이스만 호출되고 등급이 교정된다(코드 확인).

- 오탐(warn) → judge safe 반환 → 최종 safe (source=llm)
- 미탐(safe) → judge block 반환 → 최종 block (source=llm)
- 명백 safe/block → judge 미호출 (source=rule)
- 에스컬레이션 2건에 대해서만 judge 2회 호출

## 5-1. 레드팀 스트레스 결과 (P3, 정직한 한계 노출)

의미회피 위반 11건(`split=redteam`, 대표 지표엔 미포함)으로 스트레스한 결과:

- 룰 단독: 11건 중 1건만 포착(9.1%). 혈관/혈압/모공/디톡스/"하나뿐인" 등
  직접 금지어를 피한 표현에 거의 무력.
- P2 라우팅: 룰이 놓친 10건 중 3건만 에스컬레이션(30%). 나머지 7건은
  라우팅의 SEMANTIC_RISK 어휘에도 안 걸려 LLM까지 못 감(사각지대).

교훈: 미탐 방향 라우팅이 '어휘 매칭'이라 룰과 같은 키워드 맹점을 물려받는다.
레드팀 어휘를 사전에 추가하면 이 셋엔 맞겠지만 레드팀에 과적합될 뿐이다.
근본 해법은 어휘가 아니라 정책이다: food/beauty의 safe 문구 중 효능 주장
구조가 있으면(화이트리스트 제외) 넓게 에스컬레이션하거나, 값싼 의미 분류를
쓰는 방향. 비용이 오르므로 팀과 임계값 합의가 필요하다. 레드팀셋은 이 정책을
바꿀 때마다 재현율을 재는 상설 회귀 가드로 남긴다.

## 5-2. 효과 상한 분석 (oracle, `run_hybrid_eval.py`)

LLM 판정이 '완벽하다면' 현재 라우팅으로 도달 가능한 천장(upper bound).
실제 LLM은 2차 오탐으로 이보다 낮다. API 키 실측은 별도.

| split | 룰 단독 | 하이브리드(oracle 상한) | 교정 | 라우팅 사각 |
|---|---|---|---|---|
| HOLDOUT | 90.6% | **100%** | 3 | 0 |
| REDTEAM | 9.1% | **36.4%** | 3 | 7 |

- 대표 분포(HOLDOUT): 라우팅이 오류 3건을 모두 포착 → 좋은 LLM이면 천장 100%.
- 적대적(REDTEAM): 완벽한 LLM이어도 36.4%가 한계. 7건은 라우팅이 LLM에
  보내지도 않아 교정 기회 자체가 없음. → 병목은 LLM이 아니라 **라우팅 정책**.
- 검증: null judge(무동작)는 룰 단독과 정확히 일치(하니스 정상).

## 5-3. 라우팅 정책 트레이드오프 (선작업, oracle 상한 기준)

미탐 방향 라우팅을 두 정책으로 비교(`run_hybrid_eval --policy all`).

| 정책 | HOLDOUT 천장 / 에스컬레이션율 | REDTEAM 천장 / 에스컬레이션율 |
|---|---|---|
| lexicon(어휘) | 100% / 25% | 36.4% / 27% |
| broad(food·beauty safe 전수) | 100% / 50% | **81.8%** / 73% |

- broad는 레드팀 천장을 36%→82%로 올리지만, 정상 트래픽(HOLDOUT)의 에스컬레이션율이
  25%→50%로 올라 LLM 호출 비용이 약 2배가 된다.
- broad로도 안 잡히는 레드팀 2건은 goods(미신·배타성)다. broad가 food/beauty만
  커버하므로. 굿즈 회피는 별도 룰/정책 필요.
- 결정 포인트(비용 민감): API 예산이 빡빡하면 lexicon 기본 + 필요 시 broad를
  '고보증 모드'로 옵션화하는 절충이 현실적. 임계값은 팀 합의 사항.

## 6. 아직 안 한 것 (정직한 경계)

- LLM 판정의 실제 정확도는 측정 안 됨. API 키로 `build_llm_judge`를 붙여
  골드셋 3건이 실제로 교정되는지 + 정상 9건이 그대로 유지되는지 재야 한다.
- 프롬프트 튜닝, LLM 오판(정상을 위반으로 뒤집는 2차 오탐) 측정 필요.
- `/validate/copy`에 하이브리드 경로 연결(현재는 룰 + 단발 LLM opinion 구조).
